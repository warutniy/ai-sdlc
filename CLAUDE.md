## Commands

```bash
npm run dev              # start Next.js dev server (Turbopack) at localhost:3000
npm run build             # production build (also type-checks + lints)
npm run start             # run the production build
npm run lint              # ESLint (flat config: eslint-config-next + eslint-plugin-storybook)
npm run storybook         # Storybook dev server at localhost:6006
npm run build-storybook   # static Storybook build
npm run test              # vitest run — both projects (backend + Storybook, see below)
npm run test:report       # runs the full suite and (re)writes public/test-report.html
```

`vitest.config.ts` defines two projects: `server` (Node environment — unit tests in `lib/**/*.test.ts` and integration tests in `app/api/**/*.test.ts`) and `storybook` (`@storybook/addon-vitest`, runs every `*.stories.tsx` in a real Chromium browser through Playwright). Playwright's browser binary is **not installed by default** in this environment — run `npx playwright install chromium` once before the first run, or the `storybook` project fails with "Executable doesn't exist" (the `server` project is unaffected and still passes).

To run just the backend tests: `npx vitest run --project=server`. To run a single story's test: `npx vitest run -t "<story name>"`, or scope by file: `npx vitest components/farmart/Button.stories.tsx`.

`npm run test:report` shells out to `vitest run --reporter=json`, writes the raw results to `.vitest-report.json` (gitignored, kept on disk — don't delete it mid-run, editors turn Vitest's own "JSON report written to..." log line into a clickable link), then renders `public/test-report.html` from it via `scripts/generate-test-report.mjs`.

## Architecture

This is a Next.js App Router app with a small real backend (SQLite, no external services) built around one design system: **`DESIGN.md`** at the repo root. It documents every color, typography, spacing, radius, and component token as `{colors.x}` / `{typography.x}` / `{component.x}` references, plus Do's/Don'ts and known gaps. Any new UI work should read `DESIGN.md` first and update it when introducing a new visual pattern or component — the doc and `components/farmart/` are meant to stay in sync.

**Routes** (`app/`):
- `/` — the Farmart grocery homepage (`app/page.tsx` + `app/HomeContent.tsx`), assembled from `components/farmart/*`. Client-rendered: `HomeContent` (`"use client"`) fetches categories/banners/brands/products from the `/api/*` routes below on mount rather than reading the database directly, so the initial HTML is a loading shell.
- `/design` — a living style guide that renders the actual design tokens and components from `DESIGN.md` (color swatches, type scale, radius/spacing rulers, live component previews) — not a separate mockup.
- `/product` — a product detail page demonstrating the same component set (gallery, rating, tabs, related products). Still static mock data — not yet wired to the backend.
- `/docs` — Swagger UI (`app/docs/SwaggerDocs.tsx`, `"use client"`) rendering `public/openapi.json`, the OpenAPI spec for the whole API surface (implemented routes and the not-yet-built ones alike — check the spec's `paths` against `app/api/` to see which is which).
- `/mermaid.html` — static file in `public/`, not a Next.js route; a Mermaid ER diagram of the SQLite schema (mermaid.js loaded from CDN). Regenerate by hand if `lib/db.ts`'s schema changes.
- `/openapi.json`, `/test-report.html` — also static files served straight from `public/` (the latter regenerated by `npm run test:report`).

**Backend** (`lib/`, `app/api/`, `types/node-sqlite.d.ts`):
- SQLite via Node's built-in `node:sqlite` (`DatabaseSync`) — no native addon, no extra dependency. `@types/node` (pinned to v20) predates this API, hence the ambient typings in `types/node-sqlite.d.ts`.
- `lib/db.ts` — opens/creates `data/farmart.db` (gitignored, created on first `getDb()` call), owns the schema (`categories`, `banners`, `brands`, `products`) and seeds it once when `categories` is empty. The DB path is overridable via `FARMART_DB_PATH` (tests use `:memory:`); `resetDbForTests()` is a test-only escape hatch to force a reseed. See `.claude/skills/onboard-seed-data/SKILL.md` for the full seeded-data reference (counts, ids) and how to reseed/reset locally.
- `lib/farmart-data.ts` — the query layer (`getCategories`, `getBanners`, `getBrands`, `getProducts`), matching the OpenAPI `Category`/`Banner`/`BrandPromo`/`Product` schemas exactly. Both `app/api/*/route.ts` and `app/HomeContent.tsx` (client-side, over HTTP) end up calling these.
- `app/api/{categories,banners,brands,products}/route.ts` — thin route handlers over `lib/farmart-data.ts`. `products` supports `section`, `category`, `search`, `relatedTo`, `page`, `pageSize` query params (400 on an invalid `section`).
- `lib/format.ts` — presentation helpers shared between server and client code (e.g. `ratingToStars`).

**Testing**: unit tests live next to the code they test (`lib/*.test.ts`); integration tests for route handlers live next to the route (`app/api/**/route.test.ts`) and call the exported `GET` function directly against an isolated `:memory:` database (see the `beforeEach` pattern setting `FARMART_DB_PATH` + `resetDbForTests()` in any of them). Tests that assert on exact seeded counts (e.g. `total: 15`) must be updated in lockstep with `lib/db.ts`'s seed data.

**Onboarding**: `.claude/skills/onboard-seed-data/SKILL.md` is the Claude Code skill for first-time setup (install deps, reset/reseed the DB, start the dev server, verify) — invoke it (or point a new contributor at it) instead of re-deriving these steps.

**Component library** (`components/farmart/`): every exported piece is documented in `DESIGN.md` with a matching `{component.name}` reference in a leading JSDoc comment. Each component is colocated with its own `ComponentName.stories.tsx`; import everything through the barrel `@/components/farmart` (the `@/*` path alias resolves to the repo root, not `src/`). Components are plain Server Components by default; only ones that own interactive state (`Dialog`, `DialogDemo`, `QuantityStepper`, `ImageGallery`, `ProductTabs`, `SearchBox`) are marked `"use client"`. Pages stay Server Components and compose these directly — an interactive child needing local state should get its own `"use client"` leaf component (see `DialogDemo` as the pattern for wrapping a stateful demo around a controlled component, and `SearchBox`/`HomeContent` for one that also fetches its own data) rather than making the whole page client-side.

**Storybook** is scoped to `components/farmart/**/*.stories.tsx` only (`.storybook/main.ts`) — there is no `stories/` directory. `.storybook/preview.tsx` imports `app/globals.css` directly; without that import Tailwind classes silently no-op inside Storybook (components render unstyled), so don't remove it.

**Styling**: Tailwind CSS v4, zero-config — there is no `tailwind.config.ts`. `@tailwindcss/postcss` runs via `postcss.config.mjs`, and `app/globals.css` just does `@import "tailwindcss"` plus a couple of CSS variables for light/dark background. Design-system colors are applied as Tailwind arbitrary values (e.g. `bg-[#f5a623]`) rather than theme tokens, matching the hex values in `DESIGN.md`'s frontmatter. Tailwind's build-time scanner only sees class names that appear literally in source — never assemble a Tailwind arbitrary-value class from a runtime/DB value (see the `BRAND_TILE_BG` constant in `app/HomeContent.tsx` for the pattern: keep cosmetic-only variation in source, keyed by index, and let the DB hold only real content).

**`AGENTS.md`** is regenerated by `next dev` itself on every run (see the file's own header) — don't hand-edit or delete it; `CLAUDE.md` just imports it via `@AGENTS.md` above.

**`PLAN.md`** is the product roadmap (business goals and phased feature checklist for the full grocery app — discovery/browsing, listing, product detail, cart, checkout, non-functional requirements). It's planning content, not implementation status; the current codebase implements the homepage's data (categories/banners/brands/products) end-to-end through a real SQLite-backed API, plus PDP and style-guide demo slices still on static mock data.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
